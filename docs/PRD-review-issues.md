# PRD 评审问题清单

- 日期：2026-09-18
- 评审对象：`docs/PRD.md` v1.0（Pet Leather Studio）
- 用途：交由修订方（GPT）逐条处理，修订 PRD 实现方案。每条含【问题】【影响】【建议修改】。
- 分级：P0 = 影响产品成败，必须解决；P1 = 影响实施效率与一致性；P2 = 一致性小问题。
- 修订时请保持 PRD 原有的纪律风格（可测试的验收条款、禁止伪造、显式标注未验证事项），新增内容也按此标准写。

## P0-1 核心产品风险没有任何验收门："浮雕像不像这只宠物"

**问题**

- PRD 第 1.1 节自己承认"模型相似度"是主要未知因素；第 12.3 节也承认合成测试不能替代真实相似度。
- 但 F03 的全部验收条款（AC-F03-01～05）都是几何/技术指标：尺寸误差、封闭性、法向一致、无 NaN、参数可复现。**没有任何一条检验"人能否认出这是那只宠物"。**

**影响**

- 最坏情形：M1 所有 AC 全绿通过，但用户看三维预览后发现区域基函数路线生成的浮雕不像宠物，基线算法需要推翻。此时 F01/F02 的持久化、标注体系投入已经沉没。

**建议修改**

1. 为 M1 增加人工评审门，例如新增 AC-F03-06："用户本人不借助标注叠加层，仅凭正/侧视图渲染能辨认出目标宠物的五官结构；不通过则记录原因并调整基线算法后才进入 M2。"主观但必须存在，可注明"主观评审，由项目负责人执行"。
2. 在 M1 之前新增一个一次性算法 spike 里程碑（M0.5）：无 GUI、纯脚本级验证"照片 → 硬编码/手工标注 → 高度场 → 封闭 STL"。交付物是一个可打印的测试件和一个结论（基线算法路线是否可辨认），代码允许用后即弃。
3. 若用户有打印渠道，把最早的实物验证（打印一块浮雕测试件并压制皮革）提前到 M0.5/M1 阶段，而非等到 M2 才首次接触实物。两个最大未知数（照片→可辨认浮雕、模具→皮革转印）用几百行脚本 + 一次实物就能初步验证。

## P0-2 pyvistaqt 是技术栈最脆弱的一环，且冒烟失败后没有规定退路

**问题**

- 第 3.1 节选定 pyvistaqt + QtInteractor 作为三维查看主干。pyvistaqt 是社区项目，维护力度弱，QtInteractor 在 macOS（用户当前平台）有已知的嵌入崩溃、关闭异常等问题。
- 第 3.2 节要求先做冒烟测试（正确），但只说失败时"不要悄悄换成截图查看器"，**没有规定允许的退路**。

**影响**

- 冒烟失败时实施代理会临场发挥，可能做出不可控的替换或卡死在调试 VTK 嵌入上。

**建议修改**

1. 在第 3.2 节明确候选退路，按优先级排列：
   - 退路 A：绕过 pyvistaqt，直接使用 VTK 官方 QVTKRenderWindowInteractor（`vtkmodules.qt`）；PyVista 仍可用于离屏渲染与网格处理。
   - 退路 B：三维预览降级为独立窗口（非嵌入式）。
2. 明确冒烟测试必须覆盖：启动 → 显示 → 旋转/缩放 → **正常关闭不崩溃** → 连续交互数分钟无异常。macOS 上"关闭崩溃"和"长时间交互退化"是高频坑，不能只测"能显示能旋转"。
3. 把 pyvistaqt/VTK/PySide6 的具体版本锁定写入 M0 交付物，并记录选型依据。

## P0-3 高度场统一管线未写明为硬约束；毛纹分辨率与性能预算矛盾

**问题**

- F03（浮雕）、F05（毛纹）、F06（上下模）存在一条明显更优的实现路径：**一切编辑在高度场上完成，最后一次性实体化**——毛纹凹槽是高度场位移叠加，上模 = 高度场反形 + Z 向间隙，下模 = 大形体高度场。这样完全避开"先建网格再布尔运算/网格雕刻"路线（20 万面布尔运算慢且不稳定）。
- PRD 没有明说这一点。对人类开发者是常识，对 AI 实施代理不是；不写明，实施者可能选网格布尔路线。
- 数值矛盾：F05 毛纹示例线宽 0.2mm，但第 12.1 节性能预算只写了 512×512 高度场。80mm 挂件在 512 分辨率下为 0.156mm/像素，0.2mm 沟槽仅约 1.3 像素宽，**AC-F05-02 要求的"重新导入可测得对应深度"在 512 分辨率下不可能满足**。

**影响**

- 实现路线走偏导致性能与稳定性问题；或 M2 阶段才发现分辨率预算不足，返工导出与测试链。

**建议修改**

1. 在 PRD（或规划的 architecture.md 大纲）中固化为硬约束：R1 的浮雕/毛纹/模具生成统一基于高度场管线，禁止在 R1 引入网格布尔运算作为主流程（布尔仅允许用于定位柱孔等次要特征，且须注明）。
2. 修正第 12.1 节：补充"毛纹与精细节点导出需要 ≥1024（建议 2048）高度场分辨率"的预算条目，并给出该分辨率下的生成时间目标与内存估算要求。
3. 明确 LOD 策略：预览分辨率（256/512）与生产导出分辨率（1024/2048）分离，且 manifest 中必须记录导出时的实际分辨率。

## P1-4 完全没有时间/规模估计

**问题**

- R1 范围为 F01–F08：SQLite + 原子写 + revision 体系、带变换链和 undo 的标注编辑器、浮雕算法、VTK 嵌入、毛纹系统、模具生成、材料检查、试压记录。对单人 + AI 代理是以月计的工程，而 PRD 没有任何工期概念。

**影响**

- 无法判断进度是否健康；里程碑取舍（例如是否先简化持久化）没有决策依据。

**建议修改**

1. 为每个里程碑（M0–M5）增加一行粗略规模估计（例如"M1 ≈ 3–4 周（单人 + AI 代理）"），并注明估计误差范围。
2. 考虑是否将 M1 再切分：例如 M1a 用 JSON 存档跑通垂直闭环，M1b 再引入 SQLite + 完整 revision 体系。注意这会推迟 F01 部分 AC 的满足时点，属于用户决策项（见开放问题 4）。

## P1-5 草稿/未提交状态在数据模型中没有位置

**问题**

- 第 7.1 节要求"页面切换不丢失未提交草稿"，但第 6.3 节工程布局中 `revisions/` 全部是不可变产物，没有草稿存储区。

**影响**

- 实施时草稿持久化行为未定义：存内存（崩溃即丢，违反 7.1）还是私建目录（与规范不一致）。

**建议修改**

- 在第 6.3 节工程布局中新增 draft/workbench 区域（如 `workspace/<uuid>/drafts/<feature>/`），定义：草稿生命周期、崩溃恢复语义、草稿与 revision 的关系（保存版本 = 草稿固化 + 参数快照），以及草稿不入数据库主存储的原则。

## P1-6 缺少 CI 策略

**问题**

- 所有验证都依赖本机手工执行（第 11.5、16 章）。PRD 完全没有提及 CI。仓库已托管在 GitHub。

**影响**

- 纪律靠自觉；AI 代理参与的代码没有自动护栏，回归靠人肉发现。

**建议修改**

- 新增小节：GitHub Actions 在每次 push 时运行 `ruff check`、`ruff format --check`、`mypy`（domain/application）、`pytest tests/unit tests/architecture`；GUI/渲染真机测试明确排除在 CI 外、仍按第 12 章本地执行。缓存 uv 依赖。说明 CI 失败禁止合入 main。

## 开放问题（修订时须向用户确认，或给出带取舍的选项）

1. **实物验证渠道**：用户是否有树脂打印机/压机的使用渠道？若每次打样都走服务商（以周计的迭代周期），M2 策略应改为"一次打样携带多组参数的测试块阵列"，而非小步快跑。这直接影响 F05 测试块和 M2 的设计。
2. **是否接受 M0.5 算法 spike**：在 M1 之前先做无 GUI 的脚本级闭环（照片→标注→高度场→STL）+ 一次实物测试，验证两个最大未知数。用户是否接受为此推迟 M1？
3. **相似度人工评审门**：是否愿意将"用户本人可辨认"作为正式验收条款写入 AC（主观但关键）？
4. **M1 是否切分**：先 JSON 存档跑通闭环、SQLite/revision 体系后移（更快见效）vs 按现文档一次到位（更稳）？取决于用户对节奏的期望。
5. **时间预算**：整个项目的期望节奏是"尽快做出第一个能卖的挂件"还是"优先把软件做扎实"？两者在里程碑取舍上不同。
